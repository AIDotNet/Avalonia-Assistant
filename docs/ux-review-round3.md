# 交互细节优化清单（第三轮）

> 范围：`src/AvaloniaAssistant.UI` 全部页面 + 四条跨页路径（导航、审批、关窗、保存）。
> 方法：逐文件读交互代码并标行号；对前两轮声称已修的项目做一次反向核对（grep + 读实现）。
> 与 [ux-review-interaction.md](ux-review-interaction.md)、[ux-review-detail-interactions.md](ux-review-detail-interactions.md) 的关系：
> **不重复登记**。上一轮尚未落地的项目在第二节单独列账，本轮只写新发现。

## 先说结论

前两轮解决的是"看不见"：工具过程压成一行、权限变更进消息流、审批有第二处提示、MCP 真的握手。
这一轮读下来，问题换了一种形态——**界面上的状态显示，比它所描述的状态跑得快一步**：

- 标题写"正在执行"，其实早就停在审批上等你（N1）；
- 工作区胶囊显示新目录，这条任务其实还钉在旧目录（N2）；
- 关窗弹窗写"已经生成的内容会保留"，实际这半轮根本没落盘（N5）；
- 设置页提示"已保存"，那个填错的 Max tokens 根本没进设置（N12）。

用户不是被功能缺失卡住的，是被**一句不成立的说明**带错的。这类问题的代价比"少个按钮"高得多：他会在错误的前提上继续操作，
而且事后无法复现——因为界面当时说得斩钉截铁。

下面 15 条按这个主线排。优先级仍按「触发频率 × 卡住代价 × 有无替代 × 预期违背度」判定。

## 三、P0

### N1 卡在审批上，标题还在说"正在执行"

**现在**：

- `MainWindowViewModel.WindowTitle`（`MainWindowViewModel.cs:105-118`）先判断 `RunningChatCount > 0`，命中就直接返回
  `"正在执行（N）"`；`HasPendingApproval` 那条分支排在后面，**永远走不到**。
  原因是审批期间 `RunPromptAsync` 的 `IsBusy` 一直是 true（`:753` 置位，`:1008` 才复位），而审批就是在这中间阻塞的。
- `HasPendingApproval` 只看当前页：`CurrentPage is ChatViewModel chat && chat.HasPendingApproval`（`:102`）。
  于是**后台会话卡在审批上时，全窗口没有任何信号**：侧栏那一行只有转圈（`SidebarView.axaml:44-51`），
  和"正在跑"长得一模一样。

**用户看到什么**：切去写文档，回来看到标题"正在执行（1）"和侧栏转圈，以为它还在干活。实际上它二十分钟前就停了，
在等他点一下"允许一次"。如果那条会话被切到了后台，他连去哪点都不知道。

**为什么排 P0**：这是唯一一条**会让任务永久停住且无提示**的路径。Agent 阻塞在人工确认上，用户却以为在计算——
几乎所有"AI 怎么这么慢"的错觉里，这一类最难自查，因为界面上每个字都在说"它在忙"。

**目标**：审批等待必须和"正在计算"在视觉上分开，且跨页面可见。

**怎么改**：

1. `WindowTitle` 把两个判断换序：有待确认时优先返回 `"等你确认（N）"`，其次才是"正在执行"。
   两者同时存在时写 `"等你确认（1）· 执行中（2）"`，别只显示一个。
2. `HasPendingApproval` 改成扫描全部 chat（当前页 + `_backgroundChats`），计数而不是布尔。
3. 侧栏项增加第三态：`IsRunning` 之外加 `NeedsApproval`，转圈换成琥珀色的盾牌点，
   tooltip 写"等待你确认：执行命令"。`SetRunningFlag` 之外补一个 `SetApprovalFlag`。
4. 后台会话进入审批时也触发一次 `AttentionRequested`（现在只在跑完时触发，`MainWindowViewModel.cs:328-331`）。

**验收**：在会话 A 触发 `run_command`，切到会话 B → 标题出现"等你确认（1）"，侧栏 A 那一行是琥珀点；
切回 A 点允许 → 标题恢复"正在执行（1）"，点消失。全程不需要来回找。

## 四、P1

### N2 换了工作区，胶囊变了，任务没变

**现在**：输入框下面那颗胶囊读的是全局设置（`ComposerViewModel.cs:283-290`），点开浮层选目录会直接改写
`Settings.WorkspacePath`。但会话一旦发过话就"钉住"：`ApplyWorkspaceChange` 只在
`Session.Entries.Count == 0` 时才把新目录写进任务（`ChatViewModel.cs:126-135`）。

结果：**页头副标题读 `Session.WorkspacePath`（`:176-185`），显示旧目录；输入框下面读设置，显示新目录。**
同一屏两个地方说两个答案，而模型真正读写的还是旧目录。

"钉住"这个决定本身是对的（中途换目录，前面引用过的文件就对不上）。问题在于它是隐形的：
用户以为自己在给这条任务换目录，实际改的是"下一条任务的默认目录"。

**为什么排 P1**：工作区是上下文边界。找错文件、写错位置这类后果，用户会归因于"AI 不靠谱"，
而真正的原因是界面没说清它没换。

**目标**：让"这条任务钉在哪个目录"变成一句看得见的事实。

**怎么改**：

1. 会话已有内容时，胶囊上的名字后面带一个小锁形角标，tooltip 写"这条任务固定在 <路径>，切换只影响新任务"。
2. 浮层顶部加一行状态："这条任务已开始，切换工作区只对下一个任务生效"，并把当前任务目录单独列出来。
3. 未开始的会话保持现在的行为（跟着走），因为那时确实还没钉住——这层差异要让用户看见，而不是靠猜。
4. 页头副标题与胶囊必须同源：都以 `Session.WorkspacePath` 为准，设置值只在"未开始"时才参与显示。

**验收**：发一句话后打开工作区浮层 → 顶部出现固定提示，胶囊带锁；选另一个目录 → 胶囊文字不变（仍是旧目录），
新建任务 → 新目录生效。两处显示始终一致。

### N3 从对话去设置，回来找不到刚才那条任务

**现在**：三个页面的返回都写死回首页——`SettingsViewModel.Back`（`:487-497`，`SaveAndLeaveAsync` 同样 `:499-507`）、
`ToolsViewModel.cs:155`、`McpViewModel.cs:155-156`。换页时 `OnCurrentPageChanging` 会 `Dispose` 掉 ChatViewModel
（`MainWindowViewModel.cs:1217-1251`），草稿留下，但**页面和滚动位置都没了**。

最常见的链路：401 错误卡 →「去设置」→ 改 Key → 保存并返回 → 落在首页 → 在侧栏里找那条任务 → 点开 → 滚回刚才那一段。

**为什么排 P1**：错误处理是产品最该顺手的地方，这里却要求用户自己找回来。而且"去设置"这个动作恰恰发生在
用户最焦躁的时候（任务刚失败）。

**目标**：改完设置回到出事的地方，且原来的错误卡还在。

**怎么改**：

1. 导航层记一个 `ReturnPage`：`OpenSettingsAsync` / `OpenTools` / `OpenMcp` 记住来源页（含 ChatViewModel 实例），
   `Back` 优先回它，没有来源才回首页。
2. ChatViewModel 被换走时不要立刻 `Dispose`，改成和后台任务同一套：放进 `_backgroundChats`（不忙时也可以留着），
   或者干脆缓存"最近一条"以便换回。这一步要注意别把内存拖大，只留最近一条即可。
3. 从错误卡进设置时带上锚点：设置页顶部加一条 `来自「修复 502」· 返回该任务` 的面包屑，比只改返回键更明确。

**验收**：在会话里触发 401 → 去设置 → 改 Key → 保存并返回 → 回到同一条会话、同一位置，错误卡仍在（可点重试）。

### N4 点麦克风，页面跳走了

**现在**：`ToggleVoiceAsync` 在未配置时直接 `_openSettings()` 然后 return（`ComposerViewModel.cs:804-808`），
没有任何提示。而同一屏的发送按钮在同样情况下是**就地提示**（`:318-325`，"还没配模型服务…这段文字会留在这里"）。

同一类前置条件，两个控件两种处理：发送是解释，麦克风是跳转。用户点的是麦克风，得到的是一次页面切换。

**为什么排 P1**：语音是低频入口，但"点 A 得到 B"是最伤信任的一类反馈；而且它和 N3 叠加——
跳过去之后返回还是首页，等于把用户从对话里弹出去两次。

**目标**：任何按钮被按下，结果必须发生在它旁边。

**怎么改**：

1. 未配置时照发送的处理：设 `SetupHint`（"语音转写要用模型服务的 Key，先去设置填一下"），不跳页。
2. 真正要跳的地方（提示条上的「去设置」）保持跳转——那是用户主动点的。

**验收**：清空 Key 后点麦克风 → 输入框下面出现一行说明，页面不动，草稿还在。

### N5 关窗时说"内容会保留"，实际不会

**现在**：`RunningTasksDialog.axaml:54` 写的是
"已经生成的内容会保留，没跑完的这一轮不会继续。"

但落地逻辑是：流式文本只存在 VM 的 `StringBuilder` 里，写回 `Session.Entries` 是在
`RunPromptAsync` 的 `finally`（`ChatViewModel.cs:995-1004`），落盘再往后（`:1040-1048`）。
`ConfirmCloseAsync` 调完 `StopAllRuns()` 就 `Close()`（`MainWindow.axaml.cs:346-366`），
`ShutdownMode` 是默认的 `OnLastWindowClose`——进程直接退，`finally` 里的异步写盘大概率来不及。

**用户看到什么**：它说会保留，重开之后那一轮只剩一条空的助手气泡（`RegisterSessionAsync` 在第一句时就写了一个空 assistant 条目），
正文没了。他不会再试第二次，只会记住"这东西会丢东西"。

**为什么排 P1**：不常发生，但一旦发生就是内容损失，而且是被界面**明确承诺过不会丢**的内容。
比静默丢失更糟的是：它让人相信了一次。

**目标**：要么真的保住，要么把话说准。

**怎么改**（按成本取一条）：

1. **首选**：`StopAllRuns` 之后不立即关，弹窗切到"正在保存…"，等所有 `RunPromptAsync` 的 `finally` 走完（给 3 秒超时），
   再 `Close()`。实现上给 ChatViewModel 加一个 `Task Completion`，`StopAllRuns` 返回 `Task.WhenAll`。
2. 兜底：在 `finally` 之前做一次"应急落盘"——`Stop()` 里同步把当前 `assistant.Text` 写进 entry 并落盘。
   流式过程中每 N 秒也可以写一次（会话文件已经是增量结构，成本很低）。
3. 如果两条都不做，至少把文案改成"已生成的内容可能丢失"，别承诺。

**验收**：跑一条长回复，中途关窗选「停止并退出」→ 重开应用，那条会话保留到停止那一刻的正文，
不是空气泡，也不是整轮消失。

### N6 生成期间 Enter 能排队了，但另两个状态仍然"按了没反应"

**现在**：上一轮把 `IsBusy` 从 `CanSend` 里摘掉了，改走排队（`ComposerViewModel.cs:435-440`）。
但 `CanSend` 还挡着 `IsSending`（正在读引用正文）和 `IsRecording`（正在录音）：
`ComposerView.axaml.cs:159-168` 先 `e.Handled = true`，再判断 `CanExecute`，不满足就什么都不发生。

所以：录音时敲 Enter、引用三份大文件正在读时敲 Enter，仍然是**光标不动、没有换行、没有提示**。
这和第一轮 P0-1 修掉的是同一个体感，只是触发条件窄了。

**为什么排 P1**：`IsSending` 在读大文件时能持续几秒，用户很容易在这几秒里补一句话；录音时想"先发出去再说"也很自然。
修法只有几行，但留着就是一个随时会复现的"卡住了？"。

**目标**：任何一次 Enter 都有回应，且不允许出现"吞键"。

**怎么改**：

1. `IsSending` 时：把这次发送记成待发，读完引用后立刻发（和 `IsBusy` 的排队共用一条队列，只是触发时机不同）。
2. `IsRecording` 时：Enter 先结束录音并转写，不发送——但要在 `ActivityText` 里写一句"正在转写，转完按 Enter 发送"。
3. 兜底原则：`e.Handled = true` 之后必须至少产生一次可见变化（清空、提示、状态变化），不能空手而归。

**验收**：录音中按 Enter → 录音停止并出现"正在转写"；读引用中按 Enter → 出现"已排队，读完引用就发"，随后自动发出。

### N7 贴一张 4K 截图，没人告诉你要花多少钱

**现在**：`AddImage` 直接把位图存成 PNG 原图，不缩、不压、不限尺寸（`ComposerViewModel.cs:680-710`），
存完只显示一个 68×68 缩略图。一张 3840×2160 的截图落盘通常 3~8MB，进模型前会再被编码一次；
视觉模型的计费按分辨率折算 token，一张 4K 图很容易吃掉几千到上万 token。

界面上没有任何一处说这件事：缩略图 tooltip 只有 `Caption`，发送前也没有尺寸/大小提示。

**为什么排 P1**：这是 AI 产品特有的"看不见的成本"。用户按普通截图习惯操作，一次对话贴三张图，
账单和上下文一起涨，而他以为是"顺手贴一下"。

**目标**：贴图时就知道它有多大、会被怎么处理。

**怎么改**：

1. 落盘前统一缩到长边 1568px（业界常见的视觉模型输入上限），保留原图可选；缩过的在角上标一个"已压缩"小角标。
2. 缩略图 tooltip 补一行"3840×2160 · 4.2MB · 约 1.1k token"，粗略估算即可，标"约"字。
3. 单条消息超过 3 张图时，输入框下面一行"已贴 4 张，本轮请求会明显变贵"。
4. 不建议做"禁止贴大图"——挡住的是合理需求，说明白就够了。

**验收**：贴一张 4K 截图 → 缩略图角标显示"已压缩"，tooltip 有原始尺寸、大小和估算 token；贴第 4 张出现一行提醒。

### N9 删一个 MCP 服务端，连 env 一起没了

**现在**：卡片右上角一个垃圾桶图标，点一下 `Remove` 直接写 `mcp.json`（`McpViewModel.cs:367-388`），
没有确认、没有撤销。删掉的是整段配置：`command` / `args` / `env` / `headers` / `exposure`，可能还有别人给的 token。

同一个产品里，删任务是两段式确认（`SidebarView.axaml.cs:337-378`），删 MCP 是一键。反差本身就在教用户"这里不用小心"。

**为什么排 P1**（上一轮把它放在 P2，我建议提级）：低频但**不可逆**，且丢失的是难以重建的配置。
`headers` 里的 token 通常不在别处留档。

## S3 审批卡可改参数

先说清一个约束：SDK 的 `BeforeToolCallResult` 只有 `Block / Reason / Terminate`，**不能改写工具入参**
（反射确认过）。所以「改完直接执行」在当前协议里做不到，实现的是：

**改参数 → 拒绝这次调用 → 把改后的参数写进拒绝理由 → 模型立刻原样重发 → 重发那次自动放行一次。**

- `IToolApprovalGate` 返回值从 `bool` 改成 `ToolApprovalDecision(bool Allowed, string? CorrectedArguments)`。
- `PiAgentRuntime`：带改后参数时，拒绝理由写成明确指令（含完整 JSON），要求模型不要解释、不要改别的字段。
- `ApprovalMessageViewModel`：参数区变成可编辑的 `Textarea`，带「还原」「按修改重试」；
  原始参数是 JSON 的，改完必须仍是合法 JSON，否则就地报错、不发出去。
- 主按钮二选一：没改过是「允许一次」，改过就只剩「按修改重试」——两个「允许」并排，点错一次就按旧参数跑了。
- Ctrl+Enter 跟随当前内容：改过参数时提交的是眼前这份。
- 改后的参数通过 `_pendingCorrectedArguments` 记住；模型重发时按 JSON 结构比对（缩进/字段顺序不同也算相同），
  命中就自动放行一次，避免紧接着再弹一张一模一样的卡。换轮清空。

**验证**：`artifacts/r5-approval.png`（可编辑参数区 + 允许一次）、
`artifacts/r5-approval-edited.png`（主按钮切成「按修改重试」、还原出现、说明文字完整）。
`--approval-edited` 是这轮新加的截图入口。**没有跑真实模型做端到端**：需要一次真实工具调用才能看到

## N11 行内高亮（重做）

上一轮的结论是「`arc:Markdown` 不暴露分词，只能给一句上下文」。这次翻 API 注释发现控制本身就有：
`Find(query, matchCase)` 标出全部命中并把第一处设为当前，另有 `FindNext/FindPrevious`、`ClearSearch`、
`MatchCount`、`CurrentMatchIndex`、`DocumentReady`。真正卡住的是两件别的事：

1. **配色缺失**：命中底色按 `Md.SearchHighlightBackground` / `Md.SearchCurrentBackground` 两个键
   从资源里取，Arc 的主题没定义它们——命中词就只有文字、没有底。补在 `Styles/Tokens.axaml`；
   类型是 `Color`，写成 `SolidColorBrush` 一点效果都没有（试过一次，像素零变化）。
2. **时机**：正文还没进可视树、或者 Markdown 还没排完版时，`Find` 会被丢掉。现在是
   「挂 `DocumentReady` 补一次 + 找不到控件就 160ms 重试，最多 12 次」。

现在普通命中是黄底、当前命中是橙底；换关键词会把上一条消息上的旧底清掉。

**验证**：`artifacts/r7-search.png`（`--chat-search 内存`）。正文里两处「内存」都标出来了，
