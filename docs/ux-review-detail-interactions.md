> **状态（2026-10-24 15:50）**：P0-1 ~ P0-3、P1-4 ~ P1-13 已落地，逐条记录见文末「本轮修复记录」。

范围：`src/AvaloniaAssistant.UI` 全部页面 + 三条运行时路径（发送、重试、会话重建）。
方法：逐文件读交互代码并核对行号，配合 `artifacts/` 里的真实截图（`final-chat.png`、`verify-approval-pending.png`、
`verify-settings.png`、`verify-tools.png`、`home-fresh.png`）。
与 [ux-review-interaction.md](ux-review-interaction.md) 的关系：**不重复**。上一轮 P0 四条已修，本清单只记新发现；
上一轮尚未落地的项在文末单独列了一张对照表，避免重复登记、也避免误以为已经做了。

先说结论：这个产品的交互已经解决了「看得见」——工具过程压成一行、权限变更进消息流、后台任务有未读点、
重试能定位到具体某一轮。**还差的是「解释得通」**：用户对 AI 的四个基本预期，在界面上被打破时没有任何补偿。

1. **预期动作被打破**：卡片的 ↗ 看起来是"打开"，实际是"立即执行并计费"；"复制"看起来是复制内容，
   实际复制的是 Markdown 源码；贴图看起来是"给它看图"，实际模型可能根本没看见。
2. **预期边界被打破**：截断之后给的是"去设置"，而不是"接着写"；关一个工具开关，会顺带把上下文重建掉。
3. **预期状态被打破**：按停之后，那一行工具卡永远停在"运行中"；跑长任务时没有任何时间参照。
4. **预期可逆性被打破**：中间那条"重试"，会静默删掉它之后的全部轮次，且已经写盘。

下面 15 条按这个主线分组，优先级仍按「触发频率 × 卡住代价 × 有无替代」判定，
额外加一条 AI 产品特有的权重：**预期违背度**——界面的说法/图标与真实行为差多远。

# P0

## P0-1 首页建议卡：点一下就开始花钱，而图标说的是「打开」

**现在**：整张卡是一个 `Button`，命令直达 `UseCardCommand`（`Views/HomeView.axaml:125-158`），
VM 里 `UseCardAsync` 直接 `StartNewChatAsync(card.Prompt)`（`ViewModels/HomeViewModel.cs:194-195`）——
新建会话 + 立即发送。而同屏 5 个快词走的是另一套：`UseQuickPrompt` 只把文字填进输入框
（`ViewModels/HomeViewModel.cs:198-202`）。卡右上角那个 `ArrowUpRight` 只是图标，不是按钮。

用户看到「整理下载目录 / 找出大文件，按类型归类」，想先把"下载目录"改成 `D:\Downloads\临时`，
于是点了一下卡片——任务已经建好、模型已经开始跑、token 已经开始算。他连光标都没看见过。

**为什么排 P0**：首屏第一动作，每次新建任务都会看到；不可逆（会话已落盘）；
`↗` 在桌面软件里的通用语义是"打开详情/新窗口"，与实际行为正相反，是这份清单里预期违背最重的一处。

**目标**：同一屏内「填入」和「执行」必须能分辨，且"执行"要可撤销。

**怎么改**（推荐 A，成本最小）：

- A. 卡身点击 = 填入输入框并聚焦，光标停在末尾（和快词完全一致）。右上角 `↗` 换成真正可点的
  "直接运行"按钮，tooltip 写明"立即开始，消耗一次请求"。两个 affordance 分开，谁也不用猜。
- B. 保留一键跑，但发送后 3 秒内在输入框位置给一条"已开始 · 撤销"提示条，撤销即停并丢弃该会话。
  这条对"误点"有效，但对"我想先改一个字"无效，所以只作为 A 的补充。

**验收**：点卡身 → 输入框出现完整提示词、可编辑、不产生新会话；点 ↗ → 立即开跑，
1 秒内可停止，停止后侧栏不残留空任务。

## P0-2 「重试」静默删掉后面所有轮次

**现在**：`RetryFromAsync` 从被点的那条回复往前找到对应的 user 消息，然后
`Session.Entries.RemoveRange(...)`、`Messages.RemoveAt(...)` 一路删到末尾（`ViewModels/ChatViewModel.cs:542-604`），
中间没有任何确认。只有按钮的 tooltip 里写了一句"会丢弃它之后的内容"（`Views/ChatView.axaml:394-398`）。
本轮结束后 `SaveSessionAsync` 写盘（`ViewModels/ChatViewModel.cs:913`），删掉的就真没了。

一条聊了 20 轮的会话，第 3 轮回复下面的"重试"和最后一条回复下面的"重试"长得一模一样。

**为什么排 P0**：低频误触但**不可逆**，而且用户对"重试"的心智模型是"这一条重新答一次"，
不是"后面全删"。这类损失无法靠重试找回。

**目标**：只在真有东西会丢的时候拦一下；最后一轮重试保持零摩擦。

**怎么改**：

1. 判断 `Messages.Count > userIndex + 2`（这条之后还有内容）才提示，文案带上数量：
   "从这里重跑会删掉之后的 17 轮对话，删了不能恢复。" 两个按钮：「重跑并删除」/「取消」。
2. 想更稳就加撤销：删除前把 `Session.Entries` 深拷贝进一个一次性快照，输入框上方挂 10 秒
   "已删除 17 轮 · 撤销"。超时清空快照。
3. 别给最后一条加重试确认——那是高频且无损的动作，加了就是纯摩擦。

**验收**：在中间某轮点重试 → 出现带数量的确认；取消后消息数与存档条目数都不变；
最后一条点重试 → 不弹任何东西，直接重跑。

## P0-3 贴了图，模型其实没看见

**现在**：`AddImage` 只校验能不能落盘（`ViewModels/ComposerViewModel.cs:639`），不看当前模型是否支持视觉。
README 的已知边界写得很清楚："不支持的模型由 pi.net 降级成占位符，不会报错，但也看不到图。"

用户贴一张界面截图问"这个按钮间距是不是太大了"，模型回一段泛泛的可用性建议。他不会想到"图没传进去"，
只会得出"这个 AI 看图能力不行"的结论——而真相是当前模型根本不接图。

**为什么排 P0**：静默失败，且直接导致错误结论；多模态是这个产品明确的卖点之一（README 第二条特性）。

**目标**：贴图的那一刻就知道"这个模型看不看得见"，而不是发完才知道。

**怎么改**：

1. 在 `ProviderPreset` / 设置里补一个 `SupportsVision` 标记（DeepSeek 文本模型 false，Anthropic / GPT 视觉档 true）。
2. `AddImage` 时若 `SupportsVision == false`：照常收下图（不硬拦，用户可能就是想存档），
   但缩略图右上角加一枚"看不见"角标，输入框下方一行：
   "deepseek-flash 不接图片，发过去会被忽略 · 换个支持视觉的模型"。
3. 模型能力未知（自定义端点、Ollama）时**什么都不提示**——宁可不说，也不要误伤本地视觉模型。

**验收**：在 deepseek-flash 下贴图 → 缩略图有角标 + 一行说明；换成 claude-sonnet 后贴同一张图 → 无提示；
自定义端点贴图 → 无提示。

## P1-4 按停之后，那一行工具永远在「运行中」

**现在**：`ToolCallViewModel.IsRunning` 初始为 `true`（`ViewModels/MessageViewModels.cs:168`），
只有 `Finish()` 会把它置 false（`:192-201`）。用户按停止时走的是取消路径
（`ViewModels/ChatViewModel.cs:830-837`），只把 `assistant.IsStopped` 置 true；
`finally`（`:848-920`）收尾了消息、token、存档，**没有收尾 `assistant.Tools` 里还在跑的那一个**。
于是 `StatusText` 一直返回"运行中"（`ViewModels/MessageViewModels.cs:177`），`DurationText` 为空。

重启应用后从存档重建会调 `Finish(...)`（`ViewModels/ChatViewModel.cs:972`），所以这个坏状态
只活在当前进程里——恰恰是最容易被看见的那段时间：用户停完就盯着屏幕看它停没停。

**为什么排 P1**：这是真 bug，不是取舍；状态与实际相反，且没有任何出路（只能切走再切回）。

**目标**：停止 = 所有未完成工具立刻有终态，并且说清"是被你停的"，不是失败。

**怎么改**：

1. `ToolCallViewModel` 加 `Abort(long elapsedMs)`：`IsRunning = false`、`IsAborted = true`、`DurationMs = elapsed`。
2. `RunPromptAsync` 的 `finally` 里对 `assistant.Tools.Where(t => t.IsRunning)` 逐个 `Abort`。
3. `StatusText` 增加一档"已中断"，颜色用中性灰（不要红色——用户主动停的不是错误，
   这一点和现有 `IsStopped` 的处理保持一致）。

**验收**：跑一条 `run_command`，执行中按停止 → 1 秒内该行从「运行中」变「已中断 · 3.2s」，
颜色为灰；再发一条新消息，旧行保持"已中断"。

## P1-5 「复制」复制的是 Markdown 源码

**现在**：`CopyAsync` 把 `Text` 原样交给剪贴板（`ViewModels/MessageViewModels.cs:412-421`），
而 `Text` 是模型返回的原始增量拼接（`AppendText`，`:377`），渲染是 `arc:Markdown` 干的活
（`Views/ChatView.axaml:316`）。所以用户看到的表格、加粗、代码块，复制出来是
`| 文件 | 大小 |`、`**重点**`、三反引号。

让它整理一份对比表，点"复制"，粘进 Word 或微信——满屏竖线和星号，还得手动清一遍。
这是"把结果拿走"的动作，也基本是这个产品的终点动作。

**为什么排 P1**：高频、有替代（手选渲染后的文字），但替代很烦，而且用户不会预期到这一点。

**目标**：默认给人能直接粘的文本，同时不剥夺需要源码的人。

**怎么改**：

1. 主"复制"改成纯文本转换：去标题井号、去强调标记、链接留文字、表格转 tab 分隔、
   代码块保留内容去掉围栏。转换逻辑放 `Abstractions` 里做成纯函数，可单测。
2. 次级入口（按住 Alt 点复制，或复制按钮右侧的小箭头）给"复制 Markdown 源码"。
3. 代码块单独给复制——`arc:Markdown` 若不支持，就在外层套一个自定义模板，把 fenced code 渲染成
   带右上角复制按钮的块。这条可以后做，前两条先解决 80% 的场景。
4. 复制回执沿用现有的"已复制"（`:412-421`），文案区分成"已复制文本 / 已复制 Markdown"。

**验收**：复制含表格和代码块的回复，粘进记事本得到可读纯文本，无竖线无星号；
Alt 点击得到原始 Markdown；单测覆盖表格、嵌套列表、行内代码三种。

## P1-6 被截断时，最该给的按钮是「接着写」

**现在**：`AgentStopReason.Length` 触发 `SetError(..., "回复达到长度上限，已截断。")`
（`ViewModels/ChatViewModel.cs:814-817`），分类落到 `LengthLimit`，动作是「去设置」
（`Abstractions/RunErrorText.cs:73-80`）。而产品里已经有"继续写"的能力，
只是 `ShowContinue` 要求 `IsStopped && IsLatest`（`ViewModels/MessageViewModels.cs:311`），
截断不算 stopped，所以这个按钮不出现。

写方案写到一半被截断，用户面前只有一个"去设置"——他得先离开对话、找到 Max tokens、改数字、保存、回来、
再想个办法让模型接着写。而正确答案就在手边。

**为什么排 P1**：长文写作必遇；有绕法（手动发一句"继续"）但很蠢，且"继续"会新增一条用户消息，
和已有的"同一条气泡往下长"不是一回事。

**目标**：截断后的第一动作是"接着写"，改配置降为次要。

**怎么改**：

1. `LengthLimit` 的 `ActionLabel` 改成"接着写"，`HandleErrorActionAsync` 里走 `ContinueFromAsync(message)`
   （`ViewModels/ChatViewModel.cs:1110-1129`）。
2. 错误卡上补第二个次要动作"调大 Max tokens"，仍去设置。
3. 顺手把提示语改准确：不是"截断"，是"写到 4096 token 停了，可以接着写"。

**验收**：把 Max tokens 调到 200 触发截断 → 卡片主按钮为「接着写」，点击后同一条气泡继续输出，
不新增用户消息；次按钮能到设置页并聚焦 Max tokens 输入框。

## P1-7 用户消息不能改，只能重打

**现在**：`UserMessageViewModel` 是纯只读的（`ViewModels/MessageViewModels.cs:36-90`），
没有编辑命令，气泡上也没有编辑入口。

"帮我把 D:/work/project 下的日志按天归档" —— 发出去才发现路径少了一个 `s`。
现在要么重打整段，要么让它"用 D:/workspace/project 再来一次"，多花一轮上下文。

**为什么排 P1**：高频（打字错误、路径写错、少给一个条件），有绕法但每次都要重述。

**目标**：改错别字不用重述需求。

**怎么改**：

1. 用户气泡 hover 出"编辑"（和助手气泡的操作区同一套视觉，别新造一套）。
2. 点击后气泡就地变成多行编辑框，Esc 取消、Ctrl+Enter 保存；附件和图片保持原样，只改文字。
3. 保存后按"从这轮重跑"处理：复用 P0-2 的截断逻辑和确认提示，避免编辑变成另一种静默删除。
4. 已经发出去的历史轮次也能改——这正是它比"重发一条"有价值的地方。

**验收**：编辑第 2 轮提问里的一个词 → 确认后从第 2 轮重跑，第 1 轮和附件不变；
Esc 取消后原文一字不变。

## P1-8 关一个工具开关，顺手把上下文清了

**现在**：会话是否复用由 `SessionHolder.Matches` 判定，它比较权限、模型、Key、BaseUrl、协议、
`DisabledTools` 和完整历史（`AvaloniaAssistant.Agent/PiAgentRuntime.cs:495-505`）。
任何一项变了就走重建：新建 CodingAgent 会话，再用 `SeedHistory` 把历史重放一遍（`:228-230`）。
而技能页/工具页的开关只是写 settings（`ViewModels/ToolsViewModel.cs:266-276`），界面上一句说明都没有。

README 自己承认"压缩结果不跨进程保存"。所以一条已经压缩过几轮的长会话，用户随手关掉"执行命令"，
下一轮的上下文等于从头重放——更慢、更贵，甚至可能直接超长。他完全不知道这两件事有关。

**为什么排 P1**：中频、完全不可观测、代价高。而且这是 AI 产品特有的因果链：用户以为在改"工具权限"，
实际动了"记忆"。

**目标**：让"改这个会影响上下文"变成可见的因果。

**怎么改**：

1. 工具卡开关旁常驻一行小字"下一轮生效"；不再写"下一个会话"（当前实现其实是下一轮）。
2. 当前会话轮次超过阈值（建议 15 轮）时，改成"下一轮生效 · 会重建上下文（这条已 32 轮），
   可能更慢更贵"。阈值判断放 UI 层，不需要运行时事件。
3. 会话重建这件事本身值得在消息流里留一行提示（只在"因设置变更而重建"时）：
   "设置变了，上下文已重建"——和权限变更进消息流（`ChatViewModel.cs:882-892`）同一套做法。
4. 做到这一步需要运行时多暴露一个"会话被重建"的事件，建议和旧清单 P1-7 的"压缩发生"事件一起加，
   避免两次改同一个契约。

**验收**：在 30 轮会话里关掉一个工具 → 开关旁出现"会重建上下文"的说明；
下一轮开跑时消息流里有一行重建提示。

## P1-9 侧栏搜索只能用鼠标点

**现在**：`Ctrl+K` 能把焦点送进搜索框，搜索也支持按正文命中并给摘要（上一轮 P0-3 做的），
但键盘处理只接了 `Esc`（`Views/SidebarView.axaml.cs:48-52`）。输入关键字之后，选哪一条必须动鼠标。

**为什么排 P1**：`Ctrl+K` 是给"手不离键盘"的人准备的入口，现在只完成了一半；
有替代（鼠标），但替代破坏了入口存在的理由。

**目标**：从按键到打开会话，全程不碰鼠标。

**怎么改**：搜索框 `KeyDown` 里加 ↑/↓ 移动选中（结果行已有 hover 态，加一个 `selected` 类即可）、
`Enter` 打开选中项、`Esc` 清空并回到进入搜索前的会话。搜索结果为空时 Enter 不做事、不要发出声音。

**验收**：Ctrl+K → 输三个字 → ↓↓ → Enter，打开第 2 条结果，焦点回到输入框。

# 不建议做的

- **不要给每条回复加"换个模型重跑"按钮**。模型选择在输入框已经常驻，消息级再加一个，
  会让"我现在用的是哪个模型"变成三个地方各说一套。想换模型就换完再点重试，链路已经通了。
- **不要在工具卡里做"跳过这一步"**。步骤之间的依赖只在 Agent 循环里，UI 层跳过等于让后面全错。
  要干预就按停止，别做半截控制。
- **不要给"停止"加二次确认**。停止是安全动作，加确认只会让人在紧急时更慌。
- **不要把复制做成"复制渲染结果"**。渲染结果是位图或富文本，粘到代码编辑器里就废了；
  纯文本 + Markdown 两个选项已经覆盖两种用途。
- **不要在首页再加推荐位**（沿用上一轮判断）。现在 5 个快词 + 4 张卡已经在和输入框抢注意力。
